**Title:** Loom parser silently drops positional strings containing a colon, and absorbs `key=` as body text

**Body:**

Two silent failures in `dashboard/src/lib/ai/loom-parser.ts`, both from the same line. I hit the second one in production and found the first while reading the code afterwards. I have a PR ready if you want it — happy to leave it as an issue instead if the Rust parser migration makes a dashboard patch not worth reviewing.

### 1. A positional string containing a colon is destroyed

`parseBrick` (lines 766–773 on `main`) splits attributes from positional content with a substring test:

```ts
if (t.includes(':') && !t.startsWith('[')) attrTokens.push(t);
```

Any positional string with a colon anywhere in it is therefore read as an attribute, then split at `indexOf(':')`:

```
text "Runs 9:00 to 17:00"    →  props {"\"Runs 9":"00 to 17:00\""}   content: undefined
text "Docs: https://ex.com"  →  props {"\"Docs":" https://ex.com\""}  content: undefined
```

The text doesn't render wrong — it disappears, and a garbage attribute takes its place. Times, URLs, ratios and any prose using a colon hit this. `parsePhase` (line 674) has the same test and loses phase descriptions the same way.

The quick-reference example in the file's own docstring, `text "Paste your robotic draft below."`, is one colon away from vanishing.

### 2. `key="value"` is absorbed into body text

A token with no colon at all falls to the positional branch. So `title="Verify evidence"` — the natural mistake for anyone arriving from HTML, JSX, or weft itself, which binds with `=` at the outer level — becomes body copy.

A published page of mine rendered this to visitors for a day:

```
title="Verify evidence" Every finding is checked against its source data by
SHA-256 hash and JSON path before it reaches the report.
```

No diagnostic at edit, save, publish, or render. The loom in question was generated by the Tangle Runner Page Builder, which is the part I'd flag hardest: the builder makes this mistake and nothing catches it.

### Reproduction

No account needed. `tokenizeLine`, `parseAttributes` and `parseBrick`'s classifier transcribed verbatim from `main`, with cases:

https://github.com/JeremyGracey-AI/governance-drift-researcher/blob/main/loom-parser-repro.mjs

```
node loom-parser-repro.mjs
```

### Suggested fix

Classify on `^[A-Za-z][A-Za-z0-9_.-]*:` so a token is an attribute only when it *starts* with one, and push a `LoomParseError` naming the key when a bare `key=` appears. `state.errors` and `LoomParseError` already exist and are used two lines up for `Unknown brick`, so this reaches for the channel that's already there.

Both changes are local to the classifier. This lines up with CONTRIBUTING's "do not add silent fallbacks, fail loud", and with the roadmap's explicit expand/gather item — same shape of implicit behaviour that AI writers confuse and that produces wrong data quietly.
