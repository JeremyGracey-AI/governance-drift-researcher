Defect report/ Loom & WeaveMind Builder/ 19 Aug 2026/ Jeremy Gracey

The Missing Colon

A published demo rendered its own markup as body copy for a day. One character caused it, no diagnostic ever fired, and reading the parser afterwards turned up a worse bug sitting underneath it.

: Loom
= Weft · HTML · JSX

Loom attaches attributes with a colon. Every markup language it resembles — and its own sibling DSL — uses an equals sign. The parser accepted the wrong one in silence and rendered it to visitors as prose.

Routing — read before filing

These are defects in Loom, the runner-page DSL, and in the publish pipeline. The Weft compiler is not implicated anywhere in this report — it behaved correctly throughout.

Both live in the open-source repo, so this is filable there: dashboard/src/lib/ai/loom-parser.ts and crates/weft-api/src/publish.rs in WeaveMindAI/weft. Route it to the dashboard, not the language crates.

One caveat worth stating when filing: ROADMAP's “Centralize parsing and compilation in Rust” covers this exact file, and publish.rs already notes “the dashboard is the only place that understands the loom syntax.” Keep any patch small enough to survive that migration, or to carry over as a test case.

What visitors saw

The published app carries a “How it works” strip of four cards. Three rendered correctly. The second rendered its own source markup as the first words of the card, and lost its heading entirely.

Its siblings showed bold headings — Detect drift, Research impact, Human gate. Card 2 showed none. The failure was fully visible on the page and entirely invisible to the toolchain.

How it was found

Not by a linter, a test, or a warning. By looking at the page.

The demo was being audited for a separate reason — confirming whether the app URL was publicly reachable before linking it from a portfolio site. The first screenshot of the running app showed the malformed card. Source confirmation followed from the publish endpoint, which requires no authentication:

Reproducible by anyone, no account
curl https://api.weavemind.ai/api/v1/publish/by-user/\
gracey_dev/governance-drift-researcher-v2

The response carries weftCode, loomCode and layoutCode as plain strings. Grepping loomCode localized the defect to line 42 of 48.

Line 42

loomCode — feature-grid block
41 feature icon:"search" title:"Detect drift" "Compares your vendor…" 42 feature icon:"shield" title="Verify evidence" "Every finding is checked…" 42 feature icon:"shield" title:"Verify evidence" "Every finding is checked…" 43 feature icon:"book-open" title:"Research impact" "Pulls relevant papers…" 44 feature icon:"check-circle" title:"Human gate" "A reviewer approves…"

One of the file's seven title attributes used = instead of :. A scan of the endpoint after the fix returned zero = separators anywhere in the file, across all forty-odd attributes — confirming line 42 was the only one.

The failure mode, from the source

The parser is open source — dashboard/src/lib/ai/loom-parser.ts in WeaveMindAI/weft. This is parseBrick, lines 766–773:

parseBrick — the attribute/positional classifier
for (const t of rest) {
  if (t.includes(':') && !t.startsWith('[')) attrTokens.push(t);
  else if (t.startsWith('[') && t.endsWith(']')) attrTokens.push(t);
  else positional.push(parseQuotedString(t));
}

The classifier is a substring test for a colon. A token without one is not an error — it is positional content, joined into props.content. So title="Verify evidence" became prose, and the card lost its heading.

state.errors and LoomParseError already exist, and are used two lines above for Unknown brick. The error channel is there. This path simply doesn't reach for it.

The consequence is the reportable part: no error was raised at any stage — not in the editor, not on save, not on publish, not at render. A malformed attribute became public-facing copy with no signal anywhere in the chain.

Why this error, and not some other

This is not a random typo. Two independent forces push a writer — human or model — toward exactly = at exactly that position.

Separator conventions in play
LanguageAttach a value to a namePresent in this project
Loom title:"…" 48 lines
Weft (sibling DSL) runDate = Text { … } 338 lines
HTML / JSX / XML title="…" Every model's training data

Loom is a markup-shaped DSL — nested elements with quoted attributes — that uses the one separator markup never uses. And it sits in the same project as Weft, which binds with = at the outer level. Anyone fluent in either neighbour will produce = here, and nothing will tell them they were wrong.

That makes this a design finding, not just an instance. The single highest-value change is not fixing one line — it is raising a parse error on attr= inside a Loom element, ideally with a did-you-mean pointing at attr:.

Four layers, ordered from the keystroke outward. Only the first is about who typed something; the rest are why it survived.

What the human gate could have caught

Nothing. The pipeline's own governance gate covers report publication, not the UI shell around it. The Weft half of this project was version-controlled, compiler-validated and reviewed; the Loom half was generated, never diffed, never validated, and shipped. The bug lived precisely in the gap between them.

Which is the uncomfortable part, and worth stating plainly: this is a governance-drift researcher whose own interface layer drifted, silently, outside every governed surface it was built to demonstrate.

Findings, ranked

Finding 1 · Loom parser · highest value

Malformed attributes fail silently into content

attr="value" inside a Loom element raises no error at any stage and is rendered to visitors as body text. Contrast the Weft compiler, which ships thirteen validation passes and Levenshtein did-you-mean suggestions. The two halves of the same product have opposite postures toward invalid input.

Finding 2 · Loom parser · found by reading the code

Any positional string containing a colon is destroyed

The same substring test causes a worse bug, one this project happened not to trigger. Because the check is includes(':') rather than structural, a positional string with a colon anywhere in it is misclassified as an attribute, then split at indexOf(':'). Verified by running the parser's own functions:

Executed — transcribed verbatim from main
src      text "Docs: https://example.com"
content  undefined
props    {"\"Docs":" https://example.com\""}

src      text "Runs 9:00 to 17:00"
content  undefined
props    {"\"Runs 9":"00 to 17:00\""}

The text doesn't render wrong — it disappears, replaced by a garbage attribute. Times, URLs, ratios and ordinary prose all hit it. The parser's own quick-reference example, text "Paste your robotic draft below.", is one colon away from vanishing. Attribute values with colons are fine; only positional strings break.

Finding 3 · Publish pipeline · narrowed

Builder and deployment diverge with no staleness indicator

The divergence itself is correct design, and the earlier draft of this report was wrong to imply otherwise: publish.rs lines 202–219 show a deployment is a deliberately cloned projects row, so a live page doesn't mutate under visitors when someone edits the builder. That is the right call.

The gap is only that nothing surfaces it. No staleness badge, no “republish needed”, no builder-versus-deployment diff — so a fix applied in the obvious place looks like it shipped.

Finding 4 · Publish pipeline · found while fixing the above

The Overwrite button exists only where the API rejects it

Re-publishing over a live deployment works and is documented in publish.rs:207–210. Finding it does not. The Overwrite button appears only in the deployment scope, where clicking it returns “Cannot publish a deployment project. Publish its origin builder project instead.” The builder scope, where publishing is permitted, shows no Overwrite at all.

The path that works is to retype the existing slug into a form headed “Publish to a new URL” — where the field auto-fills from the project name, so after a rename the default value forks a second deployment instead of overwriting the live one. The safe action is visually identical to the destructive one, and is not the default.

Same shape as Findings 1 and 2: an interface offering something the backend won't honor, with nothing reconciling the two.

Finding 5 · Publish pipeline · now reproducible

Entering a deployment scope spends credits, every time

First noted as a one-off; it isn't. Three for three, deterministic — switching into a deployment scope starts a pipeline run with no confirmation. Each behaved correctly, suspending at the human gate and publishing nothing, so the governance holds. But there is no way to look at a live deployment without paying for a run.

Finding 6 · Publish pipeline

Public metadata defaults are poor

The live app's public name defaulted to Untitled Project, and its SEO description was seeded from an assistant chat message — it opened “I added three additional fields into the configuration.” Both were public for a day. Publishing should require a name, and should not promote conversational text into a public description.

Fixing it surfaced a related constraint: publish.rs:382 is let project_name = builder.name; with no request override, while the line below takes req.description.or(...). A deployment's description can be set at publish time; its name can only be changed by renaming the builder — renaming something no visitor sees in order to change something they do.

Both corrected on the live deployment via the re-publish path, with weft and loom verified byte-identical before and after.

Finding 7 · Publish model

Loom source has no version-controlled representation

Weft can live in a repository; Loom cannot leave the cloud project. Any team applying review or CI to a WeaveMind app can govern only half of it.

Closed on this side: the Loom is now exported from the publish endpoint and committed as runner-page.loom and runner-layout.loom. That is a workaround for a missing export/import path, not a fix.

This isn't an outside opinion

The findings above were checked against the project's own documents before being written up. They don't propose a new position — they report places where the code disagrees with one the project has already published.

Findings vs. the project's stated principles
Their document saysBearing
CONTRIBUTING.md, “What not to do”: “Do not add silent fallbacks. Fail loud.” And under node design rules: “Surface errors loudly… No silent fallbacks, no guessed defaults.” Findings 1 and 2 are that rule being broken, in the Loom parser.
ROADMAP.md, “Explicit expand / gather”: an implicit mechanism that “AI writers (and humans) confuse”, where expected behaviour “silently doesn't happen and produces wrong data” — to be fixed by making it explicit and erroring by default. The same failure shape, already decided. Loom's positional fallback is that pattern in the dashboard, and the same remedy applies.
DESIGN.md, “Dense for AI generation”: “If the AI keeps making the same mistake, the language changes to make that mistake harder to express.” A documented instance — with the platform's own builder agent as the AI.
DESIGN.md, “Opinionated by design”: some things enforced, some warnings, some overridable defaults. A bare key=value token is currently none of the three.

Smallest fix that catches both parser findings

In parseBrick's classifier: treat a bare unquoted token matching ^[a-zA-Z][\w-]*= as an error (“Did you mean key:?”), and decide positional-versus-attribute on whether the token starts with an identifier followed by : outside quotes, rather than on includes(':'). Both changes are local to one function.

Reproduction

No throwaway deployments were created. Instead tokenizeLine, parseAttributes and parseBrick's classifier were transcribed verbatim from main into a standalone script and run directly. It is committed as loom-parser-repro.mjs, so a maintainer can check both findings in one command:

Runnable, no platform account required
node loom-parser-repro.mjs

Case B reproduces the shipped defect exactly — title absent, content carrying the literal markup. Cases C onward demonstrate the colon-in-positional content loss.

Expected behavior in both: a parse error naming the line, ideally suggesting key:.

The drafts were staged publicly before submission, so the review of the report happened in the open rather than after the fact.

The publish-pipeline observations were reported alongside but not filed as issues; routing is theirs to direct. Full addendum and the runnable repro live in JeremyGracey-AI/governance-drift-researcher.

One house rule to respect before anything is submitted — CONTRIBUTING.md: “No AI-generated slop. If an AI wrote your PR, read it yourself first.” This report was AI-drafted. Every claim in it is cited to code or executed output precisely so it can be checked, and it should be, by a human, before it goes anywhere near their tracker.

The two metadata items remain live. Fixing them requires an Overwrite republish of the public URL from builder state — too blunt an instrument for a name change without first confirming the two scopes' Weft halves match.
